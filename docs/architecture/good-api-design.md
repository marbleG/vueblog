# API 设计最佳实践

本文整理自 [Everything I know about good API design](https://www.seangoedecke.com/good-api-design/)，总结了设计高质量 API 的核心原则与实践经验。

## 1. 熟悉度与灵活性的平衡

好的 API 应该是**无聊的**。API 的使用者目标是完成工作，而不是学习一个新颖的接口。理想情况下，用户应该无需阅读文档就能大致猜出如何使用它。这就是为什么 REST + JSON 如此流行——它足够熟悉。

但 API 一旦发布就很难修改，因此设计时需要克制"炫技"的冲动，优先保证稳定、直观和可预测。

## 2. 不要破坏用户空间

API 维护者的首要职责是：**不要破坏已发布的接口**。

- 可以新增字段，但不要轻易删除或修改现有字段的类型。
- 不要仅因为"更优雅"就更改接口。
- HTTP 规范中的 `referer` 拼写错误就是历史包袱，但至今未改，原因正是"不要破坏用户空间"。

## 3. 谨慎使用版本控制

API 版本控制（如 `/v1/`、`/v2/`）确实能在不破坏旧用户的情况下引入新接口，但它会带来沉重的维护负担：文档、测试、客户支持都需要乘以版本数。因此，**版本控制应作为最后手段**，而不是第一反应。

## 4. 产品价值胜过 API 完美

API 本身不是目的，而是让用户使用产品的手段。如果产品足够有价值，即使 API 设计糟糕也会有人用；反之，再优雅的 API 也救不了没人需要的产品。

同时，糟糕的产品设计会让 API 也很难优雅。例如，如果底层数据模型很奇怪，REST API 就只能暴露这种奇怪的结构。

## 5. 认证要简单

对于大多数 API，应该优先支持**长期有效的 API Key**。虽然 OAuth 更安全，但它对非专业工程师来说门槛太高。API 的用户不只是资深开发者，还可能是销售、产品经理、学生或爱好者。

## 6. 幂等性与安全重试

对于会产生副作用的请求（创建、支付、发药等），必须提供**幂等性机制**。常见做法是要求请求携带一个 `idempotency-key`：

- 服务端先检查该 key 是否已处理。
- 如果已处理，直接返回之前的结果。
- 如果未处理，执行操作并记录 key。

这样用户可以安全地重试，而不会产生重复数据。

## 7. 限流与熔断

任何通过 API 暴露的操作都可以被代码以极高频率调用。因此必须：

- 设置合理的限流（rate limiting）。
- 对昂贵操作设置更严格的限制。
- 保留临时禁用某个用户 API 的能力。
- 在响应中返回 `X-Limit-Remaining`、`Retry-After` 等元信息。

## 8. 分页策略

对于可能包含大量记录的列表接口：

- **小数据集**：可以使用 `offset` 或 `page` 分页，实现简单。
- **大数据集**：应使用 **cursor-based 分页**。通过上一页最后一条记录的游标来获取下一页，数据库可以利用索引快速定位，性能不会随页数增加而下降。

响应中最好包含 `next_page` 字段，降低消费者的实现成本。

## 9. 可选字段与 GraphQL

如果某些字段计算成本高，应默认不返回，通过 `include` 参数按需加载。GraphQL 提供了更彻底的灵活性，但代价是复杂度和学习成本。对于大多数场景，REST + 可选字段已经足够。

## 10. 内部 API 可以不同

以上原则主要针对公共 API。内部 API 的使用者是同事，人数少、可控，因此：

- 可以使用更复杂的认证方式。
- 必要时可以做破坏性变更（只要你能同步更新所有调用方）。
- 但仍然需要为关键操作考虑幂等性和限流，以避免事故。

## 总结

- 好的 API 无聊、稳定、可预测。
- 永远不要破坏已发布接口。
- 版本控制是最后手段。
- 简单认证降低使用门槛。
- 幂等性让重试安全。
- 限流保护后端。
- 大数据集使用游标分页。
- 昂贵字段默认不包含。
- 内部 API 可以根据团队情况放宽部分约束。
